1. The svelters compiler (a Rust port of the Svelte compiler) turns it into JavaScript. It runs inside the module loader, in the same process, at startup. When QuickJS reaches the `import './src/App.svelte'` in the generated entry module, the loader compiles the file on the spot, and there is no Vite or Node at run time. The page doesn't say what happens with a bundle built ahead of time. Guess: the compile step is skipped and the already-compiled JavaScript is loaded directly.

2. winit delivers the pointer press and release to the main thread, and each goes into skelter-core's dispatch as one transaction. Before any JavaScript runs, skelter-core hit-tests against the last frame's hit list, and the button's Rust kind handles hover and press state and emits `clicked` on release. Only signals JavaScript listens to become events, so `clicked` is posted to the host. A host checkpoint then runs on the same main thread, and QuickJS calls the runtime's dispatch, which finds your handler by node handle and runs `count++`. After the handler, the microtasks drain inside that checkpoint, which runs Svelte's effects and writes the new props into Rust.

3. The template effect re-runs and computes "Count: 1" (and "Doubled: 2"). The runtime compares each with the last value it wrote and sends only the changed ones to Rust as `setProp` calls on those two labels' handles. `text` is a layout-class prop, so the label is re-measured, laid out again only if its size changed, and marked for repaint. The button and box are not touched by `count++`. On the next frame those labels re-record their display lists and a commit carrying only them goes to the compositor thread, which draws it with wgpu.

4. The runtime creates a `window` node and sets its title and default size props. It builds the box, labels and button and inserts them, then calls the window's `present` method, all while the tree is still detached and no OS window exists. Then the event loop starts, and winit's app handler sees the presented window and reads title and size back from the node's props. It asks the platform for a window of that size, and when the first size is reported it makes your `window` node that window's root. A frame then runs (style, taffy layout, display lists, hit list) and the commit goes to the compositor thread, which draws it.

5. They run in JavaScript, in QuickJS on the main thread, using Svelte 5's own signals and effects, which the native runtime imports from `node_modules`. Rust never sees the signals, `$derived` graph or dependency tracking. It only sees the host ops JavaScript makes (create, insert, set a prop, listen) and so just the resulting prop values on nodes, plus whichever events and observed props are wired up.

6. Svelte compiles markup into direct calls, with fine-grained signals recording which effects read which state. When `count` changes, only the effects that read it re-run, and only values that actually changed are written to a node, so there is nothing to diff. skelter works out the cost of a write from the prop's change class (property, paint, layout, structure), which marks the node for the matching work in the retained tree. Only dirty nodes are re-recorded on the next frame.

7. The compiler checks your markup against a spec for that backend, generated from the kinds registered in Rust. The spec lists every tag, every prop with its type and change class, and every signal. This lets it reject an unknown tag or event at compile time, with suggestions, and generate the matching host calls. The spec also advertises optional capabilities such as numeric prop ids and templates, which describe what the compiler may emit.

8. The page says JavaScript runs on the main thread together with the event loop and tree, and that events are delivered at event time through a host checkpoint. It also says a synchronous event is one where JavaScript must answer before the native default continues, because the handler may cancel it. It doesn't explicitly argue why there is no separate JS thread, so this part is my inference. The price is that a long handler occupies the main thread, so the host puts a 10-second budget on each entry into JavaScript. Crossing into QuickJS also costs a function call, so the design keeps crossings to moments that need a decision. The page also says hover and scrolling stay in Rust and don't wait on JavaScript.

9. The three places are the tree (for measuring text during layout), the kinds (for shaping, via the widget services), and the compositor (for rasterising glyphs on the GPU). They share one `FontStore` so all three agree on the fonts. Otherwise measured sizes, shaped text and drawn glyphs could disagree. The page doesn't say what happens with no text system. Guess: text could not be measured or shaped, so labels would get no or wrong size and no text would be drawn.

10. The page says the app handler opens an OS window for each `<window>` the app presents, so I expect two windows at startup. Both read the same `count` signal, which lives in JavaScript, so a click would update both labels. When one closes, the other stays open, and `count` and the other window are unaffected. The process ends when the last window closes. The page doesn't say what happens to the closed window's node. Guess: it is destroyed.

11. The page doesn't mention a `--dev` flag. It says the runner doesn't watch files and has no hot reload, so every edit needs a restart, although the loader and host have an HMR compile mode and a reloader. As the page describes it, nothing would happen in the running app until you restart it. Guess: if `--dev` turned on that reloader, the module would recompile and the label text would update with `$state` kept.

12. Going from 3 to 4, `size` recomputes to `'few'` again, the same value as before. The `size` label should cause no `setProp` across the boundary, because the runtime compares each value with the last one written and drops identical ones. Even if the template effect re-runs for the other labels, `set_prop` in Rust returns at once on an unchanged value, so the size label's node is not touched. The page doesn't say how many frames render while idle. Guess: none, since nothing is dirty, and the `frames` counter (animation frames handed to JavaScript) stays 0.

13. `input` is not an element of the skelter backend. Tags name kinds registered in Rust, and there is no DOM, so HTML tags don't exist. The compiler checks every tag against the spec generated from the registered kinds. It is caught at compile time, when the loader compiles `App.svelte` at startup, as an `unknown_element` error. That is before mounting, before the event loop and before any window exists. A native widget such as `text-edit` would be needed instead.

14. The page doesn't mention "no skelter driver installed" or a host `run()`. It shows the event loop being started by `skelter_platform::run(Box::new(SveltersApp::new(embed, spawn)))`, with winit running on the main thread and `SveltersApp` as its handler that opens windows. So my best guess is that the binary should hand the embed and the compositor spawn to the skelter platform's app handler and let that run the loop, rather than calling a different backend's host `run()`.
